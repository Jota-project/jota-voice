# J Voice — HUD en Penpot

> **Estado: exploración.** Migración del plugin de Figma a Penpot, con los mismos componentes y la misma dirección visual. Sigue sin ser spec cerrada.

Archivo: **JOTA-VOICE-MAC → j-voice-mac**, páginas `Components` y `States`. Construido llamada a llamada vía el MCP de Penpot (`execute_code`), no con un plugin standalone como en Figma — Penpot no tiene el equivalente al modo "development" de Figma para correr un plugin local sin cuota, así que aquí sí se consume MCP por cada paso.

## Qué hay construido

**Componentes con variantes** (página `Components`):

- `Orb` — `State = Idle / Listening / Thinking / Speaking`. Gradiente Malva 400 → Sky 500. Listening/Speaking añaden un halo difuminado (`blur` de capa) detrás; Thinking añade un anillo discontinuo (`strokeStyle: 'dashed'`) en vez de color, porque **no existe un tono de "procesando" en la paleta** — se resolvió con forma, no con color nuevo.
- `Turn` — `Speaker = User / J`. Sin burbuja: texto flotante, kicker superior (TÚ/J) en terciario, cuerpo en secundario (User, 12.5px) o primario (J, 14.5px, domina).
- `Widget · Tool Call` — `State = Running / Done / Error`. Glifo + nombre en mono + estado. Running añade una barra de progreso. **Los tres estados se distinguen por glifo (⋯ / ✓ / ✕), no por color** — mismo motivo que Thinking: no hay un rojo/verde semántico en `dusk-core`. Si se añade un token de error/éxito más adelante, aquí es donde se aplicaría.
- `Widget · Table` — filas por flex (no Grid Layout de Penpot, por consistencia con el resto), cabecera versalitas + una línea separadora al 9% de opacidad.
- `Widget · Image` — placeholder + caption. No hay una imagen real de referencia, es un marcador.

**Estados ensamblados** (también en `Components` — ver nota de la página abajo):

- `HUD · Panel — Real (hoy)` (380px, dentro de `BG · Wallpaper + Panel`) — Header (Orb Listening + "Escuchando…"), Turn User, Turn J. **Solo lo que el sistema puede alimentar hoy** (D6): sin Tool Call, sin Table. Esta es la versión canónica — la que alimenta el prototipo end-to-end de la Fase 6.
- `HUD · Panel — Exploración (tool calls futuros)` (380px, dentro de `BG · Wallpaper + Panel — FUTURO (tool calls)`, clon del anterior colocado al lado) — la misma conversación pero con Tool Call Done + Table, envueltos en un recuadro de borde discontinuo con la etiqueta `FUTURO · SIN DATOS REALES AÚN` en malva. Es la exploración ilustrativa de cómo se vería si `jota-gateway` emitiera un evento de tool call — no implica que exista ese dato hoy. Ver Fase 5 en `docs/design/README.md`.
- `HUD · Glance` (340px) — Orb Speaking + un único turno de J. La respuesta efímera.
- `HUD · Pill` (230px) — Orb Listening + transcripción en vivo truncada.

**Fondos de contexto + interacciones** — cada estado insertado dentro de un board de fondo real (wallpaper degradado, documento blanco, editor oscuro), con click-through prototipado entre los tres: Pill → Glance → Panel → Pill (dissolve, 420ms entrada / 240ms salida, mismo ritmo que en Figma).

## Por qué todo está en la página `Components`

Se probó a separar "piezas" de "estados ensamblados" en una página `States`, pero **el Plugin API de Penpot solo permite modificar la página que el usuario tiene abierta en su pestaña del navegador** — cualquier intento de tocar una página distinta falla con `Cannot modify a page that is not currently active`. Se decidió (2026-08-02) no reabrir esa página: todo el archivo vive en una sola página, `Components`. Los boards de nivel superior llevan nombres con `·` para agrupar visualmente sin depender de páginas (`HUD · Panel`, `Widget · Tool Call`, `Preferencias · Avanzado`, etc.).

## Trampas del Plugin API de Penpot que ya nos han mordido

Análogas a las de Figma, pero distintas en el detalle. Vale la pena leerlas antes de tocar esto:

**`shape.applyToken()` no hace nada si el shape no está seleccionado.** Aplicar un token de color a un shape recién creado, sin más, es un no-op silencioso — ni error ni cambio. Hay que hacer `penpot.selection = [shape]` inmediatamente antes de `shape.applyToken(...)`. No está documentado; se encontró comparando un `before`/`after` de `.fills` que salían idénticos.

**`shape.x` / `shape.y` son siempre coordenadas absolutas de página, nunca relativas al padre**, incluso después de un `appendChild`. Mover un shape a un board que está en `(700, 1900)` y ponerle `x = 40` no lo coloca a 40px del borde del board: lo coloca a 40px del origen de la página, muy lejos del board, y `clipContent` lo recorta en silencio — el export sale en blanco sin ningún error. Hay que sumar la posición del padre: `shape.x = parent.x + relativo`. `boardX`/`boardY` sí son relativos, y sirven para verificar esto después del hecho.

**El recálculo de auto-layout (hug) es asíncrono.** Leer `board.height` justo después de poner `flex.verticalSizing = 'auto'` y añadir hijos casi siempre devuelve el alto del placeholder, no el real. El valor correcto aparece en la siguiente llamada a `execute_code` (con el viaje de ida y vuelta de por medio), no antes. No es un bug del build, es tiempo de layout — conviene releer antes de exportar o combinar en variantes.

**`createVariantFromComponents` ya crea una propiedad por defecto.** Llamar a `variants.addProperty()` después añade una segunda de sobra ("Property 2") que se queda sin usar en todas las variantes. Basta con `variants.renameProperty(0, '<Nombre>')` sobre la que ya existe. Si se comete el error, `variants.removeProperty(pos)` la quita sin rehacer nada más.

**El contexto de ejecución (`storage`) se ha reiniciado dos veces en esta sesión sin aviso**, perdiendo todo lo cacheado entre llamadas — no perdió nada del documento real en Penpot, solo las referencias JS en memoria. La recuperación es barata: releer por `page.findShapes({name: ...})` en vez de fiarse de que `storage` sobrevive de una llamada a la siguiente. Por eso el patrón de este build es "cachear en `storage` para ir rápido, pero saber reconstruirlo desde el documento si desaparece".

**Los boards de fondo (contexto) también se han visto afectados por el bug de coordenadas absolutas** — las líneas decorativas del documento y del editor, y los tres estados anclados, aparecieron invisibles la primera vez por la misma razón que el punto anterior. Quedó resuelto sumando la posición del padre en cada colocación.

**`penpot.createText(...)` no acepta `(x, y, texto)` como los ejemplos de otras APIs de plugin sugerirían.** La única firma que funciona es `penpot.createText('texto')` — un único string. Pasar `0` como primer argumento falla con `Value not valid: 0. Code: :createText`. Tras crearlo, hay que fijar `fontId`, `fontFamily` y `fontVariantId` a la vez (p. ej. `'gfont-inter'` / `'Inter'` / `'600'`) — un `fontFamily` con pila CSS completa (`'Inter, system-ui, sans-serif'`) falla con `Value not valid: ... Code: :fontFamily`, tiene que ser el nombre exacto de una única fuente cargada.

**Añadir un shape nuevo con `appendChild` dentro de un board con auto-layout lo mete en el flujo del flex por defecto**, aunque se le pongan `x`/`y` manualmente después — el resultado es que el board padre crece para acomodarlo como si fuera un hijo más en la pila (le pasó a `HUD · Panel`: pasó de 395px a 664px de alto solo por añadir una etiqueta y un recuadro pensados como overlay). Antes de posicionar a mano un hijo nuevo en un padre con flex, hay que sacarlo del flujo con `shape.layoutChild.absolute = true` (y `horizontalSizing = 'fix'`) — el mismo patrón ya documentado para los puntos de `Window Title Bar`, pero aplica también a shapes recién creados, no solo a los que ya existían.

## Auditoría contra la skill `penpot-workflow` (2026-08-02)

A partir de esta fecha, todo el trabajo en Penpot sigue el estándar fijo de la skill `penpot-workflow` (páginas `01 · Tokens` / `02 · Components` / `03 · Screens`, naming sin notas de trabajo incrustadas, tokens obligatorios sobre color hardcodeado, estados como variantes no como interacción). Primera pasada de auditoría sobre lo ya construido:

**Corregido en esta pasada:**
- Dos shapes de texto huérfanas en la raíz de la página (restos de intentos fallidos de `penpot.createText(...)` durante la Fase 5) — eliminadas.
- El recuadro y la etiqueta del badge "FUTURO · SIN DATOS REALES AÚN" usaban un hex suelto (`#9A87CE`) en vez del token `hud.accent.active` — reaplicado con `shape.applyToken()`.
- Un board `HUD · Panel` vacío (0 hijos, huérfano, sin interacciones que lo referenciaran) en la raíz de la página — eliminado.
- Notas de trabajo incrustadas en nombres (`[mover a States]`, `— Real (hoy)`, `— Exploración (tool calls futuros)`, `— FUTURO (tool calls)`) — movidas al campo **Annotation** de cada shape; los nombres quedaron limpios (`HUD · Panel`, `HUD · Glance`, `HUD · Pill`, `HUD · Panel · Concepto tool calls`, `BG · Wallpaper + Panel · Concepto tool calls`).

**Reestructuración en 3 páginas — en curso (confirmada el 2026-08-02):**
- Creadas `01 · Tokens`, `02 · Components`, `03 · Screens` (además de la ya existente `Components`, pendiente de vaciar).
- `penpot.openPage(page)` SÍ permite cambiar la página activa por script (a diferencia de lo que se pensaba inicialmente) — pero **`appendChild` entre páginas sigue sin funcionar en ninguna dirección**, incluso con la página destino activa: el shape de origen tiene que pertenecer a la página activa para poder moverse, así que mover contenido de una página a otra no es scriptable. Se comprobó empíricamente antes de intentar la reestructuración completa.
- Consecuencia: `01 · Tokens` se pudo construir por completo por script porque es contenido **nuevo** (swatches de color/spacing/radius/opacidad/tipografía, cada uno con `shape.applyToken()` real — 7 secciones, ~85 tokens documentados). `02 · Components` y `03 · Screens`, en cambio, necesitan que el usuario mueva el contenido ya existente de `Components` con cortar/pegar nativo de Penpot (`Cmd+X` en el board, cambiar de página, `Cmd+V`) — eso sí conserva tokens, variantes e interacciones, a diferencia de cualquier intento de reconstrucción por script.
- Reparto acordado: `02 · Components` recibe Orb, Turn, Widget · Tool Call/Table/Image, Button, Switch, Text Field, Dropdown, Slider, Section Header, Tab, Chip, Window Title Bar. `03 · Screens` recibe los 3 `BG · ...` (contextos del HUD) y las 4 `Preferencias · ...`.

**Nueva trampa del API encontrada durante la reestructuración:** aplicar `applyToken(...)` dos veces seguidas sobre distintas propiedades del mismo shape (p. ej. primero `['fill']` y después `['strokeColor']`) solo deja registrado en `shape.tokens` el vínculo de la última llamada — la anterior desaparece del mapa aunque el valor de color siga siendo correcto visualmente. No se ha encontrado la causa raíz; para producción, aplicar todos los tokens de un shape en una única secuencia sin relecturas intermedias y verificar con `shape.tokens` al final, no asumir que persiste tras la siguiente llamada.

**Diseño de las tarjetas de color, v2 (feedback directo del usuario sobre la v1):** la primera versión metía un cuadradito de color dentro de una tarjeta blanca/oscura con texto al lado — el usuario pidió tarjetas a sangre completa del color real, con el texto superpuesto y un borde + sombra "muy, muy discretos" solo para separar la tarjeta del fondo de página (crítico para los blancos, que si no quedan indistinguibles del fondo gris claro de la sección). Implementado: cada tarjeta usa `shape.applyToken()` para el color real, calcula la luminancia relativa del color ya compuesto sobre el fondo de su sección para decidir si el texto va en blanco o casi-negro, y añade un stroke al 8% de opacidad + un drop-shadow sutil (blur 3, opacity 0.06). Para los tokens HUD que son `rgba(...)` con alpha < 1 (p. ej. `hud.fill.hover`, `hud.surface.veil`), se recuperó el alpha real desde `token.value` (el `resolvedValue` de Penpot colapsa a hex opaco y pierde la transparencia) y se compuso visualmente sobre el fondo oscuro real de esa sección — así el swatch muestra fielmente cómo se ve el token en producción, alpha incluido, no un cuadrado opaco engañoso.

## Preferencias pasa a tema oscuro (2026-08-03)

A petición directa del usuario ("quita ese modo de color blanco tan feo y sobrio... dale más estilo y una tonalidad dark"). Cambios:
- Los 22 tokens `prefs.*` se redefinieron en el catálogo vivo de Penpot y en `tokens/j-voice-mac.tokens.json` (ver ese archivo para el detalle completo y el razonamiento de contraste). Reutiliza el ink de marca del HUD (`ink.900`/`ink.700`) pero opaco — Preferencias es una ventana real, no un overlay de vidrio.
- Se añadieron dos primitivos nuevos a `dusk-core`: `global.color.danger.300` (#FF6659, texto/borde de error sobre oscuro, 5.9:1) y `global.color.danger.900` (#33201F, fondo de campo con error sobre oscuro) — el `danger.500` original solo daba 2.6:1 sobre `ink.900`, insuficiente para texto.
- `prefs.button.primaryBg` se separó deliberadamente de `prefs.accent.primary`: con texto blanco encima, `malva.400` (el accent normal sobre oscuro) solo da 3.1:1 — falla AA. Se usa `malva.500` ahí en su lugar (4.64:1), aunque como accent "desnudo" (texto/iconos/track) sigue siendo el 400 el correcto.
- Los tres puntos de "semáforo" de `Window Title Bar` pasaron de un gris neutro genérico a los colores reales de macOS (`#FF5F57`/`#FEBC2E`/`#28C840`) — no son tokens de marca, son convención de sistema operativo, así que se dejaron como valores fijos a propósito.

**Trampa nueva, la más cara de esta sesión:** cambiar el `.value` de un token ya existente en el catálogo (`token.value = '...'`) actualiza `token.resolvedValue` correctamente, pero **no propaga sola a los shapes que ya tenían ese token aplicado** — sus `fills` se quedan con el color antiguo indefinidamente hasta que se les vuelve a llamar `shape.applyToken()` explícitamente. Peor aún: un barrido masivo con `analyzeDescendants` + `applyToken()` sobre ~150 shapes a la vez perdió el vínculo de token (`shape.tokens`) en al menos un shape sin avisar, dejando su color desactualizado y sin binding. Para este rediseño se abandonó `applyToken` como mecanismo de propagación masiva y se hizo un recolor directo (`shape.fills = [...]`) recorriendo cada board por nombre/contexto — más verboso, pero fiable. Conclusión práctica: **la mayoría de los componentes de Preferencias construidos en la Fase 3/4 nunca tuvieron binding de token real pese a estar íntegramente basados en los valores de los tokens** — solo un puñado de shapes en `Button` lo tenían. Si se retoma este archivo, vale la pena una pasada dedicada a aplicar tokens de verdad (no solo su valor resuelto) shape por shape, con verificación tras cada aplicación, antes de fiarse de que cambiar un token en el futuro baste.

## Fase 6 — prototipo end-to-end (2026-08-03)

Construido en `03 · Screens`: `Flow · 01 Menu` (menú de la barra de estado con las 2 entradas nuevas), `Flow · 02 Pill` → `03 Panel Listening` → `04 Panel Thinking` → `05 Panel Speaking` → `06 Glance`, todos sobre el mismo fondo de escritorio (el degradado de `BG · Wallpaper + Panel`) para que el ciclo se sienta como una sola ventana que evoluciona, no una serie de contextos distintos — con `Slide` entre los estados del HUD y `Dissolve` solo en el cierre del ciclo (Glance → Menú), que sí es un salto de contexto real.

**Trampa: los destinos de `addInteraction` no pueden apuntar a un board de otra página, ni guardando la referencia en `storage` de antemano.** Se intentó cachear el board `Preferencias · General` (en la página `02 · Components`) mientras esa página estaba activa, cambiar a `03 · Screens`, y usar esa referencia cacheada como `destination` de una interacción — falla con `Value not valid` igual que el ya documentado bug de `appendChild` entre páginas. Un prototipo click-through real que cruce páginas no es construible por MCP; **todas las pantallas que se van a enlazar entre sí por interacciones tienen que vivir en la misma página**. Consecuencia práctica: las 4 pantallas de Preferencias (hoy en `02 · Components`) necesitan moverse a `03 · Screens` (cortar/pegar nativo, igual que la reorganización anterior) antes de poder enlazar "Preferencias…" del menú y el cierre de la ventana con el resto del flujo.

**Trampa: la animación `dissolve` en `addInteraction` falla si no se le pasa `easing`, pese a que la documentación del tipo `Dissolve` lo marca como opcional (`easing?`).** `{ type: 'dissolve', duration: 450 }` → `Value not valid`; `{ type: 'dissolve', duration: 450, easing: 'ease' }` → funciona. La animación `Slide` no tiene este problema si ya se le pasa `easing`, pero por seguridad conviene pasarlo siempre en ambas, ya que el mensaje de error no señala qué campo falta.

**Trampa de layout más terca que las anteriores:** en una de las siete secciones (`Prefs · Color`), el recálculo de auto-layout (`flex.verticalSizing = 'auto'`) se quedó atascado en el alto del placeholder (100px) durante *varias* llamadas seguidas de `execute_code` — algo más persistente que el retraso de un solo "viaje de ida y vuelta" ya documentado arriba. Ni relecturas, ni esperas (`setTimeout`), ni tocar `rowGap`/`columnGap`, ni vaciar `penpot.selection` lo desatascaron. Lo que sí funcionó: forzar `verticalSizing = 'fix'`, ponerle a mano un alto calculado (número de filas × alto de tarjeta + gaps + padding), y solo entonces volver a `verticalSizing = 'auto'` — ese ciclo fix→resize→auto “reinicia” el motor de layout y, en la mayoría de los casos, el valor que reporta después ya es el real (a veces incluso corrige el número hacia abajo si la estimación manual se pasó). Si un board con flex/grid se queda pegado en un tamaño placeholder pese a releer varias veces, este es el siguiente paso, no seguir reintentando lecturas.

**Nueva trampa del API encontrada durante esta pasada:** `shape.applyToken(token, ['strokeColor'])` (o `['fill']`) resetea la opacidad de *todo* el array de `fills`/`strokes` a `1` en cada llamada — no solo la propiedad de color. Si se necesita una opacidad distinta de 1 sobre un color ligado a token, hay que aplicar el token primero y fijar la opacidad después con una reescritura directa de `shape.strokes`/`shape.fills`; eso sí, esa reescritura directa borra el registro de qué token está ligado en `shape.tokens` (aunque el valor de color siga siendo correcto) — es una limitación conocida y aceptable para anotaciones puntuales, no para componentes de producción que necesiten que el token se pueda re-resolver si cambia de valor.

## Lo que falta frente al plugin de Figma

- **Sin Smart Animate.** La API de interacciones de Penpot (`addInteraction`) solo ofrece `Dissolve / Slide / Push`, no una interpolación de propiedades por capa con el mismo nombre. El prototipo usa `dissolve` como aproximación más suave; no hay forma de ver el ensanchamiento real de pill → panel dentro de Penpot mismo, solo el corte con crossfade.
- **Sin color semántico de error/éxito.** Tool Call y Orb resuelven sus estados por glifo o forma en vez de color porque `dusk-core` no define ningún tono de advertencia o confirmación. Si esto se vuelve un problema real de legibilidad, hace falta decidir un color y añadirlo a `dusk-core.tokens.json`.
- **No se ha verificado el theme de `Dusk-core`** (activar sets + crear theme `Mode/Dark`) — se hizo en `j-voice-mac`, pero quedó pendiente replicarlo en el archivo compartido.
